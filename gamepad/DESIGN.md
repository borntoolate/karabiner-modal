# ゲームパッド版の設計判断

8BitDo SN30 Pro をサブ入力デバイスにする設定です。`vim/` `emacs/` とは
**性質が違います。** あちらはキーボードの上にモードを重ねる設定ですが、
こちらは物理的に別のデバイスを足す設定で、キーボードのキーを一つも潰しません。
Caps Lock も使わないので、**Vim モードや Emacs モードと同時に有効にできます。**

---

## 1. 前提は D-input モードであること

Karabiner のゲームパッド対応は 14.13.0（2023-12-09）で入りました。リリースノートに
こう書かれています。

> Gamepad support (DirectInput devices are supported. Xinput is not supported at all)

**X-input モードのコントローラーは Karabiner から見えません。** デバイス一覧にすら
出ないので、「設定が効かない」ではなく「デバイスがない」という形で失敗します。

SN30 Pro は `Start + B` を3秒長押しで D-input に入ります。接続後、Karabiner-Elements
→ Devices で **Modify events** を ON にしないと、Karabiner がデバイスを掴みません。

---

## 2. ボタン番号は実測した。推測してはいけない

DirectInput のボタン番号は機種とモードで変わります。ドキュメントを探しても
「SN30 Pro の A ボタンが button いくつか」は書かれていません。
Karabiner-EventViewer で1つずつ押して記録しました。

| ボタン | イベント | | ボタン | イベント |
|---|---|---|---|---|
| A | `pointing_button: button1` | | Select（−） | `button11` |
| B | `button2` | | Start（＋） | `button12` |
| X | `button4` | | ハート | `button13` |
| Y | `button5` | | 左スティック押込 | `button14` |
| L | `button7` | | 右スティック押込 | `button15` |
| R | `button8` | | 十字 ↑ | `generic_desktop: dpad_up` |
| L2 | `button9` | | 十字 ↓ | `dpad_down` |
| R2 | `button10` | | 十字 ← | `dpad_left` |
| 星 | **何も出ない** | | 十字 → | `dpad_right` |

`button3` と `button6` は欠番です。並びが連番でないので、**A=button1 なら B=button2、
という素朴な推測は途中で破綻します。** 実際、最初に一括で押して記録したときは
押し順とイベントの対応が1つずれ、肩ボタンの割り当てを取り違えかけました。
2回連打で区切って取り直して確定させています。

**星ボタンは HID イベントを一切出しません。** ハートを2回、3秒あけて星を2回押して
EventViewer を見ると、ハートのぶんだけが出て（`button13` のルールが発火した ⌘Space として）、
星のぶんは何も出ませんでした。8BitDo の FAQ によると、星は Switch 以外につないだときは
**Turbo（連射）の機能ボタン**で、連射を付けたいボタンを押しながら星を押すと有効になります。
ファームウェアが食うので Karabiner には届きません。同じ計測で
**`button13` がハートであること**も確定しています。

### `generic_desktop` は from に書ける

十字キーは `pointing_button` ではなく `generic_desktop` として届きます。
この種別を `from` に書けることは**公式ドキュメントに記載がありません。**
`from` の説明ページに並んでいるのは `key_code` / `consumer_key_code` /
`pointing_button` の3つだけです。

実機で確認しました。`{"from": {"generic_desktop": "dpad_up"}, "to": [{"key_code": "f18"}]}`
だけのルールを作って有効化し、十字キー↑を押すと EventViewer に F18 が出ることを
確認しています。記載がないだけで、動きます。

## 3. なぜ `karabiner.json` を直接書き換えるのか

`make install-vim` は `assets/complex_modifications/` に JSON を置くだけで、
有効化は Karabiner の UI で手動です。ゲームパッド版は `make install-gamepad` で
`karabiner.json` を直接書き換えます。理由は2つあります。

**スティックの効きは complex_modifications では表現できません。** カーソル速度も
スクロール速度もデッドゾーンも、`karabiner.json` の `profiles[].devices[]` に書く
デバイス設定です。assets に置ける形式がありません。ルールだけ配って
「速度は GUI で設定してください」では、他の Mac に持っていったときに再現しません。

**ルールが6本あります。** assets 方式は「Add rule」を1本ずつ押す運用で、しかも
一度追加したルールは `karabiner.json` にコピーされるため、**assets 側を直しても
反映されません。** 消して追加し直す必要があります。割り当てを直すたびにこれを
やるのは現実的ではありません。

`apply.py` は description が `[SN30]` で始まるルールだけを入れ替えます。
Vim モードなど既存のルールには触りません。書き込み前に `automatic_backups/` へ
バックアップを取ります。

## 4. すべての manipulator に `device_if` を付ける

**これが一番危険な箇所です。** ゲームパッドの A ボタンは `pointing_button: button1`
として届きますが、これは**実マウス・トラックパッドの左クリックとまったく同じイベント**
です。`device_if` を付け忘れたルールを1本でも入れると、**トラックパッドのクリックが
死にます。**

`gen.py` の `manipulator()` が必ず `device_if` を先頭に入れるので、
**JSON を手で書かないでください。** `make check` は綴りと評価順は見ますが、
`device_if` の付け忘れまでは見ません。

## 5. レイヤー構成

ボタンは15個しかありません。2段構えにします。

| | 役割 |
|---|---|
| 単押し | **固定ベース。** キーボードとマウスの代わり（矢印・Enter・Esc・Delete・Backspace・Tab・コピペ・クリック・アプリ切り替え） |
| L2 | 音声入力の開始 / 終了（マイクキーを送出） |
| R2 押しっぱなし | レイヤー2（変数 `sn30_mod`）。エンジニア業務のアプリで変えてよいのはここだけ |
| R2 + L2 | 口述の下書きを開く（prompt-refiner の `dictate` を `shell_command` で呼ぶ）。どのアプリでも同じ。整形は開いた TextEdit の R2 層で |
| L / ハート 押しっぱなし | 本物の修飾キー ⇧ / ⌘ |

使う場面が2つあるので、アプリを2組に分けています。

| 場面 | アプリ | 何が変わるか |
|---|---|---|
| 楽な姿勢でのエンジニア業務・ブラウジング（キーボードとマウスから脱却） | Claude Desktop / ターミナル / Claude Code / ブラウザ / その他すべて | 単押しは固定。R2 レイヤーだけ `APPS` で上書き |
| 机に向かうデザイン・音楽制作（左手デバイス） | Figma / Photoshop / Illustrator / After Effects / Logic | `DESK_APPS` で単押しも R2 も上書き。書かないボタンは固定ベースに落ちる |

どちらでも**ハートは ⌘Tab（押しっぱなしで ⌘）、R2 + ハートは Spotlight** で変わりません。
机に向かっていてもアプリ切り替えはコントローラーでできる必要があるからです。
`gen.py` は `DESK_LOCKED` でハートの上書きを拒否します。

### 単押しを固定にした理由

最初は8アプリ × 2レイヤーの全ボタンをアプリごとに出し分けていました。左手デバイス
（キーボードの隣に置く補助入力）としては筋が通っていましたが、狙いが「音声入力と
組み合わせてキーボードとマウスから脱却する」に変わった時点で前提が崩れました。
主入力デバイスなら汎用の操作はコントローラー自身が持たなければならず、それが
アプリごとに変わると覚える負担がそのまま効率を食います。実際にそうなりました。

一方で「アプリによっては優先したい割り当て」は本当にあるので、R2 レイヤーだけを
アプリ別に上書きできる形にしました。上書きできるのは 10 枠（A・十字・L / R・Start・
両スティック押込）で、メニューバー / 取り消し / やり直し / 切り取り / Spotlight の
5 枠（`MOD_LOCKED`）はどのアプリでも同じです。編集の芯と、枠のない操作への逃げ道が
アプリで動かないようにするためで、`gen.py` が上書きを拒否します。

デザイン・音楽制作のアプリは例外です。机に向かってキーボードとマウスを使う前提なので、
コントローラーは汎用入力ではなく左手デバイスに特化させ、単押しも上書きします
（`DESK_APPS`）。割り当ては一般的なショートカットに基づく初期案で、実機未検証です（§9）。

### Claude Desktop は独立した層

エンジニア業務でいちばん使うのは Claude Desktop の Code タブで、複数のセッションを並列に
回します。最初はターミナル / Claude Code のグループに入れていましたが、そこの R2 層は
CLI 向け（⌥Enter で改行、⌃C で中断、⌘K で画面クリア）で、Desktop ではどれも要りません
（改行は L + A の ⇧Enter、中断は B の Esc）。Desktop 専用の層に分けました。

キーは推測ではなく、インストールされている Desktop 2.2553.1 の `app.asar`（アプリメニューの
accelerator）と、その中身が読み込む claude.ai の Web 層のショートカット一覧（Help →
Keyboard Shortcuts、⌘/ で開くシート）から取りました。**Chat / Cowork / Code の切り替えは
⌘⌥← / ⌘⌥→**（Web 層の `chorus_surface_prev / next`。デスクトップ限定で、macOS では
分割ビュー中も効く）、**サイドバーは ⌘B**（View メニューの accelerator。⌘. も Web 層で同じ）、
**新規セッションは ⌘N**（File メニュー。Chat タブでは新規チャット）、**前後のセッションは
⌘⇧[ / ⌘⇧]**（Go メニューの Previous / Next Session。⌃Tab / ⌃⇧Tab でも同じ）、
**コマンドパレットは ⌘K**（「セッションを検索 / 開始」）、**右に新しいセッションは** `⌃⌘\`
（View → Split View）。

「既存のセッションを分割ビューで開く」だけはキーがなく、一覧に `alt+click` と書かれて
います。⌥ を立てるボタンはない（L は ⇧、ハートは ⌘）ので、**R2 + 左スティック押込を
⌥クリック**にしました。`to` は `{"pointing_button": "button1", "modifiers": ["left_option"]}` で、
`to.modifiers` が `pointing_button` にも効くことは 16.3.0 の `to_event_definition.hpp` で
確認しています（修飾キーを押してからボタンを送る）。押し込みでポインタが跳ねる問題は素の
クリック（L3）と同じで、それ以上ではありません。この枠の既定は ⌘S（保存）ですが、Desktop に
保存するものはないので潰して構いません。⌥クリックは Claude Desktop にしか置きません。
Chrome では ⌥クリックがリンクのダウンロードなので、グローバルにはできません。

権限プロンプトはルールを足していません。Web 層では「今回は許可」が ⌘Enter、拒否が Esc
なので、**ハート + A** と **B** で押せます。⌘1〜9 でのセッション指定、ペインの切り替え
（⌘⇧D / ⌘J / ⌘⇧B）はキーボードに残しました。ペインはヘッダーのアイコンからも開けます。

`open claude://code/needs-input` という入口もあります（Dock メニューの "Sessions Waiting
for You" と同じ。返事を待っているセッションのうち、いちばん長く待っているものへ飛ぶ）。
並列作業には向いていますが、`shell_command` になるので **整形中に押すと走っている
`refine` が強制終了されます**（§5 の LIMITATION）。それを避けて置いていません。要るなら
R2 + 十字 ↓ の ⌃⌘\ と入れ替えるのが順当です。同じ理由で、サーフェスの切り替えも
`open claude://claude.ai/code` のような deep link ではなくキーで送っています。

### ⌘N と ⌘S はグローバル（R2 + 右 / 左スティック押込）

TextEdit / VS Code で新しいファイルを開きたい、という要望に対して、アプリ別に置くか
グローバルに置くかを比べました。

| | アプリ別（TextEdit / VS Code だけ） | グローバル（`MOD_DEFAULT`） |
|---|---|---|
| 置き場 | TextEdit の R2 層は口述の整形で埋まっていて、空いているのは L / R（タブ送り）だけ。VS Code とは別の枠になる | 右スティック押込。既存の 9 枠を食わず、押し込みでポインタが跳ねても ⌘N は困らない |
| 覚えること | アプリごとに「新規」の位置が違う | どこでも同じボタン |
| 他のアプリで押したとき | 既定（⌘A など）のまま | Chrome / ターミナル / Finder は新しいウィンドウ、Claude Desktop は新しいセッション、Slack は新しいメッセージ。どれも「新しく作る」で、要らなければ × をクリックするか R2 + B のメニューバーから閉じる |
| 机に向かうアプリ | 影響なし | Photoshop / Illustrator / After Effects / Logic は新規書類のダイアログが開く。B（Esc）で閉じる |

⌘N は macOS で「新規」の意味がほぼ揃っている珍しいキーなので、グローバルにしました。
アプリを足すたびに配線しなくて済み、TextEdit の枠も食いません。Claude Desktop の R2 + A も
⌘N で、こちらは要望の「新規セッション」を一番押しやすい位置に置いたものです。同じキーが
2か所にあるのは承知のうえです。

**⌘S（保存）は同じ理屈で左スティック押込です。** 要るのは TextEdit（口述の下書き）と VS Code
（ターミナル / Claude Code のグループ）で、どちらも R2 層に空きがなく、2 つのアプリで位置が
違う配線になります。⌘S は ⌘N と並んで「意味がアプリで揃う」キーで、間違って押しても
困らない（保存するものがないアプリではダイアログが出るか何も起きず、ダイアログは B で
閉じる）ので、押し込みでポインタが跳ねる枠に置けます。右が「新規」、左が「保存」で対になり、
アプリを足しても配線が要りません。左スティック押込はそれまで「既定を置かず、アプリ別にだけ
置く枠」（`MOD_APP_ONLY`）でしたが、⌘S を既定にしたので区別をなくしました。Claude Desktop
の ⌥クリックは既定を上書きする普通の形になります。ブラウザで ⌘S を押すと「ページを保存」の
ダイアログが出ますが、B で閉じるだけです。

### メニューバーは R2 + B（⌃F2）

コントローラーには 15 個しかボタンがなく、R2 層はアプリごとに埋まっています。載せていない
操作（Claude Desktop の Go メニュー、ブラウザの履歴、TextEdit の書式、Save As、Close…）に
キーボードなしで届く経路が一つ要ります。macOS にはそのための標準ショートカット
**⌃F2「メニューバーにフォーカスを移動」**があり、Apple のキーボードショートカット一覧に
「矢印キーでメニューを移動し、Return で開く / 決定」と書かれています。コントローラーでは
十字 ← → でメニューを選び、↓ か A で開き、↑ ↓ で項目を選んで A で実行、B（Esc）で抜けます。
B が「入口」と「出口」を兼ねるので、覚えることは一つです。

**置き場は R2 + B、上書き不可（`MOD_LOCKED` の 5 つめ）です。** 逃げ道なので、R2 層が
いちばん埋まっているアプリでこそ要ります。アプリ別に上書きできる枠に置くと、まさにそこで
消えます。上書き不可にできて、実機で確認済みの層（Claude Desktop / ブラウザ）が使っていない
枠は B だけでした（X / Y / Select / ハートは既に不可、右スティック押込は ⌘N）。B にあった
⌘W（閉じる）は譲ります。閉じるは × をクリックするか、メニューバーの File → Close で届きます。
ブラウザでタブを閉じる頻度が高ければ、ブラウザ層の R2 + 左スティック押込（そこでは ⌘S は
要らない）に ⌘W を置く余地はあります。ターミナルのグループは B に ⌃C を置いていたので、
Start へ移しました。Start にあった ⌘K（画面をクリア）は見た目だけの操作なので外しました。

**F キーは fn の有無で 2 本にします。** Karabiner は入力を「Simple Modifications →
Complex Modifications → **Function Keys** → macOS のショートカット」の順に処理します
（公式「Input event modification chaining」）。Function Keys の段は複雑な変更の**後**に
掛かるので、`to` に素の `f2` を書くと、macOS の「F1、F2 などのキーを標準のファンクション
キーとして使用」が OFF の環境では画面の明るさに化けます。公式の "Details on changing to
function keys" どおり、その設定が OFF なら `fn` 付き、ON なら `fn` なしを送り、どちらが
効くかは変数 `system.use_fkeys_as_standard_function_keys`（15.2.3 以降）で分けます。
`gen.py` は `to` に F1〜F12 を含む枠をすべてこの 2 本に展開します（`manipulators()`）。
この Mac は設定が ON（`defaults read -g com.apple.keyboard.fnState` が 1）なので、発火するのは
fn なしの `⌃F2` です。

捨てた案は 3 つです。R2 の `to_if_alone`（他のボタンを押さずに R2 を離すたびにメニューバーへ
飛ぶ。Tab を置かなかったのと同じ理由）、ステータスメニュー側の ⌃F8（枠がない。Wi-Fi や
Control Center はスティックで指してクリックできる）、Help メニューの検索 ⌘⇧/（文字入力が
要る）。macOS 側で「メニューバーにフォーカスを移動」のショートカットを ⌘Esc に変えれば
ルールなしで **ハート + B** が同じ意味になり B の枠を空けられますが、この設定を触らせる
前提を増やしたくないので、既定の ⌃F2 のままにしました。

### ブラウザはアドレスバーとブックマーク

R2 + 十字 ↑ が ⌘L（アドレスバー = 検索欄の選択）、↓ が ⌥⌘B です。⌘L は Chrome / Safari /
Firefox / Brave / Arc のどれでもアドレスバーの選択で、公式のショートカット一覧どおりです。
⌥⌘B は Chrome では「ブックマーク マネージャーを開く」（`chrome://bookmarks` が新しいタブに
開く）、Safari では「ブックマークを編集」で、どちらも一覧がタブに出てスティックで指せます。

Chromium のソース（`chrome/browser/resources/bookmarks/`）で確かめた挙動: 1クリックで選択、
ダブルクリックで開く。**macOS では Enter が名前の変更**（`addShortcut_(Command.EDIT, 'F2',
'Enter')` の第3引数が Mac 用）、⌘O が開く、⌘Enter が新しいタブで開く、Delete / Backspace が
削除です。コントローラーでは押込 2 回で開き、A（Enter）は押さない、X / Y は削除なので
押さない、とマニュアルに書きました。Safari のブックマーク編集も Return が名前の変更です。

⌘⇧B（ブックマーク バーの表示 / 非表示）は置きませんでした。押すたびに状態が反転する
キーで、バーが出ているのか消えているのかをボタン側は知らないので、「開く」の意味には
なりません。バーを常に出したい人はキーボードから一度切り替えれば、以後はバーの項目を
1クリックで開けます。

### L とハートは本物の修飾キー

`L` は押している間 ⇧、`ハート` は押している間 ⌘ を立てます（`lazy` なので単押しでは
何も出ません）。修飾キーを本物にすると、十字・クリック・Enter・スクロールと**勝手に
合成される**ので、選択（⇧矢印）・範囲選択（⇧クリック）・行頭行末（⌘矢印）・
⌘クリック・⌘スクロールのズームを個別に割り当てずに済みます。lazy な修飾キーは
次のキー・ボタン・スティック操作の直前に送られます（16.3.0 の
`post_event_to_virtual_devices.hpp` で確認。スティックの動きにも送られるので
ハート + 右スティックでズームが効きます）。

そのために全ルールの `from.modifiers` を `optional: ["any"]` にしています。
押されている修飾キーがそのまま `to` に運ばれる挙動で、`CLAUDE.md` が vim 版の事故として
挙げているものと同じですが、ここでは狙いです。副作用として、L を握ったまま
Select を押すと ⌘⇧C になります（Chrome では要素の検証）。

ハートの単押しは `to_if_alone` で ⌘Tab です。押したまま R（Tab）を押せば ⌘ が
立ったまま Tab が続くので、スイッチャーを出したまま順送りできます。専用の変数は
要りません。Spotlight は R2 + ハートです。単押しで出していた時期は、R2 なしで
押すたびに開いて邪魔でした。

⌘Tab を `R2 + 左スティック押込` に置いた時期もありました。押し込むときにスティックが
傾いてポインタが跳ねるので、やめました。スティックの押し込みには「押しても困らないもの」
しか置けません。

### R は Tab、⇧Tab は L + R

スティックで細かくポインタを合わせるより、Tab でフォーカスを送るほうが確実な場面が
多いので、R を Tab にしました。⇧Tab は L（⇧）+ R で出ます。Claude Code の権限モード
切り替え（⇧Tab）もこれです。Tab が macOS のボタンにもフォーカスを移すには、
システム設定 → キーボード → 「キーボードナビゲーション」を ON にしておく必要があります。

十字キーに Tab を置く案は捨てました。矢印は音声入力した文を直すのに必須で、
失えないからです。同じ理由で、十字キーでマウスポインタを微動させる案（Karabiner の
`mouse_key`。待ちなし・タップで数 px・押しっぱなしで一定速度）も採用していません。
微動は左スティックのナッジ（§6）で賄います。L2 / R2 の単押し（`to_if_alone`）に
Tab を置く案も捨てました。R2 は他のボタンを押さずに離すたびに Tab が出て、L2 は
単押しが音声入力の開始 / 終了なので空いていません。

### 長押しで繰り返すのは矢印と削除だけ

キーボードでは押しっぱなしのキーが macOS のキーリピートで連打されます。ゲームパッドで
同じにすると、A を少し長く押しただけで Enter が連打され、R2 + B ならウィンドウが
次々に閉じます。そこで `to` の `repeat` を既定で `false` にし、矢印・PgUp / PgDn・
Backspace / Delete（`REPEAT_KEYS`）だけ繰り返すようにしました。押している間だけ
効かせたいキー（Photoshop の手のひらツール = スペース）は `"hold:spacebar"` と書きます。
クリックは押している間ドラッグになるので、もともと対象外です。

これは R（Tab）を押したまま L（⇧）を押したときの挙動への答えでもあります。以前は
R を押し続けると Tab がリピートし、あとから押した ⇧ は lazy なので次のキーまで
送られず、Tab の連打に見えました。今は R は1回しか出ません。⇧Tab は L を先に
押してから R です（キーボードと同じで、修飾キーが先）。

### L2 は音声入力のマイクキー

**R2 をレイヤーキーに使うのは、アナログトリガーだからです。** 押し込みが深く、
他のボタンと違って「押しながら」の姿勢が自然に取れます。A や B を修飾キーにすると、
単押しとの区別で必ず遅延が要ります。L2 はその対になる位置にあるので、もう一つの
「他と混ざらない」操作、音声入力の開始 / 終了に当てています。

L2 が送るのは `consumer_key_code: dictation` です。Apple のキーボードのマイクキー
（F5）と同じ HID イベント（consumer usage 0xCF）で、macOS の音声入力はこれで起動・
終了します。システム設定 → キーボード → 音声入力 の「ショートカット」（⌘ を2回、など）
には依存しないので、そちらは何を選んでいてもかまいません。Karabiner の公式ルール集にも
同じ `to` を使う "Map Keychron Dictation Key on Mac" があります。

最初は F13 を押している間だけ送る Push-to-Talk にしていました。音声入力アプリ側の
ホットキーを F13 に設定する前提で、F13 なら素の macOS が何にも使っていないから
どのアプリとも衝突しない、という理屈です。しかし実際に使うのは macOS 標準の音声入力で、
そちらにはホットキーを自由に設定する口がありません（修飾キーの2回押しか、マイクキー）。
macOS の音声入力は押すたびに開始 / 終了するトグルなので、L2 もトグルです。

`COMPARISON.md` §5 の「Figma などの除外アプリは設定しない」はモード全体を
アプリで無効化しない、という判断です。ここでやっているのは無効化ではなく、
**R2 レイヤーにアプリごとの意味を与える出し分け**なので、抵触しません。

### 口述は R2 + L2 で始め、整形は TextEdit の R2 層で

口述した文は prompt-refiner で構造化プロンプトにします。喋った文を `claude -p` で用途別の
構造化プロンプトに整形する作者の CLI で、**非公開です**（ローカルでは `~/works/prompt-refiner`。
このリポジトリには入っていません）。`dictate` が新しい下書き `~/prompt-log/draft-<日時>.md` を
作って TextEdit で開き、`refine <mode>` が
クリップボードを読んで `claude -p` で整形し、クリップボードへ書き戻します。コントローラーでは
**R2 + L2 が `dictate`、TextEdit が前面のときの R2 + 十字 ↑ ↓ ← → が
`refine code` / `research` / `doc` / `ticket`、R2 + Start が `refine message`** です
（並びは prompt-refiner のホットキー ⌥⌘1〜5 と同じ）。`to` は
`{"shell_command": "$HOME/bin/refine code >/dev/null"}` の形です。

**prompt-refiner 自身のホットキー（⌥⌘V / ⌥⌘1〜5）を送る形にはできません。** Karabiner は
自分が出力したイベントを再度 manipulate しないので（event modification chaining）、
ボタンから ⌥⌘1 を送っても prompt-refiner 側のルールは発火しません。コマンドを直接
呼ぶしかなく、`gen.py` の `to` 指定に `shell:` の形を足しました。`shell_command` は
`/bin/sh -c` で実行され、渡る環境変数は `$HOME` などごく少数です（公式ドキュメント。
16.3.0 の `shell_command_handler.hpp` で確認）。`claude` の PATH とロケールは
`refine` が自前で補うので、こちらで export するものはありません。環境変数を継がない
ことの裏返しで、Karabiner から呼んだ `dictate` は `PROMPT_REFINER_EDITOR` を見ず、
必ず既定の TextEdit で開きます。TextEdit 層はこれを当てにしています。

**整形ボタンは TextEdit にしか置いていません。** 最初は `refine code` / `research` を
全アプリの R2 + スティック押込に固定していました（枠が空いていなかったのと、押し込みで
ポインタが跳ねても整形はクリップボードを読むだけで困らないため）。しかし 5 モード全部を
載せる枠はなく、`doc` / `ticket` / `message` はキーボードに残ることになります。
起点を固定すると解けます。`dictate` は必ず TextEdit を開くので、整形ボタンは
「TextEdit が前面のとき」にだけあれば足り、そこなら R2 層の 9 枠を口述専用に使えます
（下書き窓でページ送り・単語移動・タブ送り・書式なし貼り付けは要りません）。全アプリで
固定するのは R2 + L2 だけになり、それは 15 ボタンの枠の外です。`MOD_LOCKED` は
編集の芯の 4 枠に戻り（その後メニューバーの B を足して 5 枠）、机に向かうアプリ
（`DESK_APPS`）に整形の枠が漏れることもなくなりました。

R2 + L2 が空いていたのは、L2 のルールに `sn30_mod` の条件がなかったからです。R2 を
握っていても L2 はマイクキーでした。L2 = 口述の開始 / 終了、R2 + L2 = 口述の場を
開く、と意味がつながるので、ここに置きました。両手の人差し指で押せます。

捨てたのは「TextEdit 以外で口述した文をコントローラーだけで整形する」経路です。
Claude Desktop の入力欄やブラウザの textarea で直接口述しても、そこでは R2 + A が
⌥Enter / ⌘T に上書きされていて ⌘A が押せないので、もともとキーボードが要る経路でした。
そちらは ⌥⌘1〜5 のままです。

**⌘A → ⌘C を整形ボタンに畳み込んでいません。** Karabiner の `to` はキーイベントを
順に出しますが、`shell_command` は即座に走り、`refine` はその場で `pbpaste` します。
⌘C がアプリに届く前にクリップボードを読む可能性があり、順序を当てにできません。
まとめるなら prompt-refiner 側に「⌘A ⌘C を打ってから読む」口（`--grab` のようなもの）を
足す必要があり、それはあちらのリポジトリの作業です。⌘S → `refine --from draft` も同じで、
`sleep` を挟めば動きそうですが同じ賭けです。⌘V の自動化も同じで、整形が終わるのは
数秒後、その間にフォーカスが動きえます。

**標準出力は捨てています。** Karabiner は `shell_command` の stdout / stderr を
`console_user_server.log` に記録します（先頭 256 文字）。`refine` は整形結果を
標準出力にも流すので、捨てないと案件名を含みうるプロンプトがログに残ります。
stderr は残るので、`入力が空です` などのエラーはログで追えます。

`LIMITATION:` **Karabiner は `shell_command` を同時に1つしか走らせません。** 走っている
間に別の `shell_command` が呼ばれると、走っているほうが強制終了されます（公式ドキュメント
「running multiple shell commands」。`shell_command_handler.hpp` では `run()` のたびに
`process_` を作り直しています）。整形は数秒〜十数秒かかるので、その間にもう一度
整形ボタンや R2 + L2 を押す、あるいはキーボードの ⌥⌘V / ⌥⌘1〜5 を押すと、先の整形は
結果をクリップボードに書かずに消えます。通知「整形完了」を待ってから次を押してください。

`LIMITATION:` **`dictate` は毎回新しい下書きを作ります。** 前の口述に言い足す
`dictate --keep`（いちばん新しい下書きをそのまま開く）はボタンにありません。
要るならキーボードから呼びます。

### 口述の 6 ボタンは prompt-refiner 側に移さない

このリポジトリは公開（MIT）で、prompt-refiner は非公開です。ゲームパッドの README を
prompt-refiner の語彙（`dictate` `refine` ⌥⌘1〜5）で書くと、読者は辿れない前提を押しつけられます。
それを理由に 6 ボタンの配線を prompt-refiner のリポジトリへ移すことを検討し、やめました。

- **6 / 175 です。** prompt-refiner を呼ぶ manipulator は 175 件中 6 件（`dictate` ×1、
  `refine <mode>` ×5）。残りのスティック・矢印・修飾キーの合成・机のアプリの層は無関係で、
  `shared/validate.py` `leakcheck.py` `make_cheatsheet_pdf.py` `Makefile` も vim / emacs と共有しています
- **6 ボタンだけ切り出しても単独で成立しません。** `sn30_mod` 変数、`device_if`（§4）、
  「TextEdit 層は汎用 R2 層より前」という評価順、`apply.py` の `[SN30]` 一括置換に依存しています。
  別リポジトリの asset から同じデバイスへ書くと、評価順が Karabiner GUI で有効化した順に
  左右され、`validate.py` の到達不能検出もリポジトリを跨げません
- **依存の向きは今のままが正しい。** 入力デバイスがツールの CLI を呼ぶ形で、prompt-refiner 側も
  ホットキー層を差し替え可能（Karabiner のキーボードルール / Raycast / ショートカット.app）と
  設計しています。ゲームパッドはその一つです。移すと、ツールがデバイスのレイヤー変数を知る
  逆向きの依存になります

代わりに**境界を契約として書きました。** ここが当てにするのは `$HOME/bin/dictate` と
`$HOME/bin/refine {code|research|doc|ticket|message}` というパスと引数、クリップボード経由の
入出力だけです。生成と検査（`make gamepad` / `make check`）には要らず、無い環境では
この 6 ボタンだけが無音で失敗します（`/bin/sh` のエラーが `console_user_server.log` に残る）。
README にはこの契約だけを書き、prompt-refiner が何かは一文で済ませています。
差し替え点は `gen.py` の `shell()` / `refine()` / `DICTATE` に集めてあります。

`LIMITATION:` **モード名 5 つと並びは prompt-refiner の事実を写した固定値です。** あちらで
モードを増やしても名前を変えても `gen.py` は追従しません。生成時に prompt-refiner を読む形は、
`gen.py` が素の `python3` だけで動くことと公開 / 非公開の分離を壊すのでやりません。
同期は手作業で、prompt-refiner 側のモード追加手順が `gen.py` の `DICTATION_APP` を指す
逆向きの参照に頼ります。

## 6. 「倒してから動くまでのラグ」の正体

Karabiner はスティックを2通りの方法で動かします。16.3.0 の
`game_pad_stick_converter.hpp` を読んで確認したもので、推測ではありません。

1. **ナッジ** — 傾きが「増えた」ぶん × `flick` だけ、HID レポートが届くたびに動く。
   待ちはない。戻す動きと、傾きを保ったままの回転では動かない
2. **連続移動** — 傾きが `continued_movement_absolute_magnitude_threshold` 以上になると
   タイマーが回り、倒している間ずっと `傾き × slow` で動き続ける

**連続移動のタイマーは、開始間隔が 300 ms にハードコードされています。** しきい値を
超えるとタイマーが起動し、最初の発火は捨てられ、300 ms 後の2回目で最初のイベントが出て、
そこで初めて `interval_milliseconds` に切り替わります。しかもタイマーが回り始めた時点で
ナッジは止まります。つまり **しきい値を超えてから 300 ms は何も動きません。**
ソースには `// TODO: Replace hard-coded interval` とあり、設定項目はありません。
main ブランチでも同じです。

これまでの調整は、この 300 ms の空白の**位置**を動かしていただけでした。

| deadzone / threshold | 何が起きるか |
|---|---|
| 0.10 / 1.00（Karabiner 既定） | 途中はナッジだけ。いっぱいまで倒して 300 ms 後に動き続ける |
| 0.08 / 0.8 → 0.08 / 0.2 | しきい値を超えた瞬間にナッジが止まり、300 ms の空白のあと動き続ける |
| 0.05 / 0.05 | 倒した瞬間に空白が始まる。「倒してから動き出すまでの待ち」が最長になる |

「倒してから動き出すまでの待ちを 0 にする」は、**連続移動については設定では不可能**です。
待ちなしで動くのはナッジだけです。

### いまの設定

左スティックはしきい値を **0.9** に上げ、初動をナッジに任せています。`flick` を 150 に
上げてあるので、倒した量に応じてその場で動き（いっぱいまで倒すと約 130 px）、
いっぱいに倒したまま保持したときだけ 300 ms 後に連続移動に入ります。
「ちょっと触ればちょっと動く」をナッジで実現する形です。しきい値だけ上げて `flick` を
既定のままにすると、ナッジが 10 px 程度で見えず、「いっぱいまで倒さないと動かない」
という Karabiner 既定の感触に戻ります。2つは一緒に動かす必要があります。

右スティックは比較用にしきい値を deadzone と同じ **0.05** のまま残してあります。
倒して 300 ms 後から動き続ける、これまでどおりの挙動です。スクロールはナッジの量が
1行に満たず、動き続けることに意味があるので、こちらの形が合う可能性があります。
両方を触り比べて、合うほうに揃えてください。**実機での体感は未確認です**（§9）。

### 設定で動かせるもの・動かせないもの

- **300 ms** — 動かせない。Karabiner のソースを直すしかない
- **しきい値** — 空白が「どこで」始まるかを決める。低いほど早く動き続けるが、ナッジの範囲が狭くなる
- **`flick`** — ナッジの量。いっぱいまで倒したときの移動量は (threshold − deadzone) × flick
- **`slow`** — 連続移動の速さ。傾き × slow ピクセルが `interval` ごとに出る
- **`interval`** — 動き出してからの粒度。動き出すまでの待ちには効かない
- **`mid` / `fast`** — 傾きは 1.0 で頭打ちなので単独では発火しない。連続移動中にもう片方の
  スティックも倒すと、その傾きが足されて 1.5 / 2.0 を超える。つまり「もう片方を倒すと加速」
- **デッドゾーン** — ドリフトとのトレードオフ。下げるほど軽いが、スティックが劣化すると
  指を離してもカーソルが動き続ける。0.05 にしてある。ドリフトが出たら 0.12〜0.2 に上げる

タイマーは両スティックで1本を共有します。片方が連続移動している間、もう片方はナッジも
連続移動も出ません。**同時には使えない**ということです。

USB-C で有線接続すると Bluetooth の 10〜20 ms は消えますが、300 ms は残ります。
有線では VID / PID が変わる可能性があり、そのときは `device_if` もスティック設定も
当たりません。試すなら先に Karabiner の Devices で識別子を確認してください。

## 7. `CHEATSHEET.md` も生成物にした

`vim/` `emacs/` の `CHEATSHEET.md` は手書きですが、**ゲームパッド版は `gen.py` が
生成します。** リポジトリの慣習からの意図的な逸脱です。

理由はずれです。当初はアプリ別 8 層で 200 通り以上あり、手で表を維持すると
必ずどこかがずれました。層を減らした今も、割り当てと説明を同じ行に持つ `gen.py` から
表を組めば、CLAUDE.md の「キー割り当てを変えたら CHEATSHEET.md も必ず更新してください」
というルールが自動で守られます。

代わりに `gen.py` の `BASE` / `MOD_DEFAULT` / `APPS` が各割り当てに説明文を持っていて、
そこから表を組みます。
割り当てと説明が同じ行にあるので、ずれようがありません。

`CHEATSHEET.md` を手で直しても次の `make gamepad` で消えます。

`CHEATSHEET.md` は早見表というよりマニュアルです。使い始めの手順、ボタンの位置図
（ASCII。日本語を混ぜると桁がずれるので図の中は英字だけ）、スティックの効き、
HID の対応表まで入っています。**PDF に載るのは表だけ**なので、位置図や手順は
Markdown で読んでください。

### HTML 版はやめた

一時期、ボタンの位置図と横断検索のついた `CHEATSHEET.html` を同じデータから
生成していました。アプリをタブで切り替える形にしたところ、**一度に1アプリしか
見えず一覧性に欠ける**と使う本人が判断したので外しました。Markdown なら全アプリの表を
上から下まで一度に眺められます。

## 8. 実装しなかったもの

| | 理由 |
|---|---|
| スティックの斜め方向に別の意味を割り当てる | Karabiner のスティックはカーソルとスクロール専用で、`from` に書けない |
| L2 / R2 のアナログ値（押し込みの深さ）を使う | ボタンとしての on/off しか `from` に書けない |
| ハートボタンでのレイヤー切り替え（トグル） | 状態が見えないため。押している間だけ、のほうが事故が少ない |
| 2ストローク（`dd` 相当） | ボタンが少なく、R2 レイヤーで足りている |
| 振動フィードバック | Karabiner に出力の口がない |
| 星ボタンへの割り当て | D-input では HID イベントを一切出さない（§2）。ファームウェアの機能ボタン |
| 連続移動の 300 ms を設定で消す | Karabiner にハードコードされている（§6）。直すならソース側 |
